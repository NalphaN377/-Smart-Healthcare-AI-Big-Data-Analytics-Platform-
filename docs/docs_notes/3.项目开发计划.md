## 2. 项目概述

### 2.1 项目背景和目标

本项目基于美国纽约州 SPARCS 医院住院患者出院公开数据集（33 个字段，覆盖医院信息、人口统计学信息、就诊信息、诊断/DRG 编码、支付方式、费用等），构建一套医疗大数据分析与 AI 大模型分析平台。系统将原始 CSV 数据经「清洗 → 入库 → 多维分析 → API 化 → 自然语言交互 → 图表可视化」的完整大数据链路，最终实现用户以自然语言提问即可获得文字洞察与动态图表的核心目标。

项目需按 CMMI3 / RUP 过程规范实施，使用 Git 按功能进行版本控制。大数据处理与分析是主线，AI 模块定位为辅助交互入口。

### 2.2 项目范围

本项目包含三大核心模块：

| 模块 | 职责 | 一期 | 二期 |
|---|---|---|---|
| 模块一：数据预处理与持久化 | 原始数据读取、清洗、标准化、去重、入库 MySQL | 大数据批量读取、异常处理、类型标准化、结构化入库 | 数据质量评估、备份恢复、增量更新 |
| 模块二：大数据分析服务 | 多维聚合、算法封装，RESTful API 对外服务 | 多维度聚合分析、算法封装、统一 JSON 响应 | 复杂分析、API 缓存（Redis）、参数校验与异常处理 |
| 模块三：AI 智能交互 | 自然语言入口，解析意图 → 调用 API → 生成摘要与图表 | LangChain 意图解析、文本摘要、ECharts 配置生成、聊天式 Web 界面 | 意图优化（准确率≥90%）、多轮对话、可视化进阶、LLM 本地化部署 |

### 2.4 约束和假设

1. **运行环境**：实训单机环境，以 Pandas + MySQL 为实现主线；Hadoop/Spark/Hive 以"预留接口 + 文档说明"方式满足设计要求，不搭建真实集群。
2. **LLM 部署**：一期调用云端 LLM API；二期可选 Qwen/BaiChuan + FastAPI 本地化部署。一期开发阶段若无 API Key，使用 AI 层的模板摘要 fallback 保证流程可跑通。

## 4. 项目的已定义过程

### 4.1 项目的生命周期选择

本项目生命周期采用 RUP 模型，结合实训场景进行裁剪：将 RUP 四阶段（初始、细化、构造、移交）压缩为 5 个迭代阶段，迭代之间以可运行产物作为里程碑。

### 4.2 项目阶段划分及主要工作产品

| 阶段 | 周期 | 主攻角色 | 主要工作产品 |
|---|---|---|---|
| 阶段 0：环境 + 契约 | 第 1 周 | ① | git init、环境安装、三份契约定稿（DB schema / API 契约 / 列名映射）、MySQL 建表 |
| 阶段 1：数据打通 | 第 2 周 | ② | 清洗入库流水线跑通、1 万条样例数据集、数据结构说明 |
| 阶段 2：服务 + 前端 | 第 3 周 | ③⑤ | 全部聚合 API 可用、统一 JSON、前端聊天界面成型 |
| 阶段 3：AI + 联调 | 第 4 周 | ④ | `/api/chat` 闭环（意图 → API → LLM 摘要 → ECharts）、前后端联调 |
| 阶段 4：二期 + 报告 | 第 5~6 周 | 全员 | 二期加分项按优先级选做、过程文档收尾、集成测试 |

## 7. 开发计划

### 7.1 项目监控计划

#### 7.1.1 活动安排

每周定期对项目的规模、进度、质量、风险进行跟踪、评审和审计，实行的机制：

- 每周开始前由 PM 发放周工作计划清单；
- 每人每天填写工作日志；
- 每周召开一次 15 分钟会（进度 / 阻塞 / 下一步），PM 更新任务看板；
- 项目结束后完成《11.项目开发总结报告》。

#### 7.1.2 偏差控制（项目计划变更与重估计约定）

| 偏差项 | 预警阈值 | 干预阈值 | 干预措施 |
|---|---|---|---|
| 进度偏差 | >±15% | >±20% | 度量分析 |
| 质量偏差 | 测试通过率 <90% | <80% | 度量分析 |

### 7.2 质量保证计划

- 质量目标：聚合 API 正确性、统一 JSON 格式一致、前端无阻塞 Bug、文档与实现一致。
- 实施方式：谁写的代码谁写单元测试；接口联调由 PM/架构师协调；每里程碑做一次质量抽查。

### 7.3 配置管理计划

见《1.配置管理计划书》。需要重点关注：

- Git 分支模型：`main` 只放稳定版本，开发用 `feature/data|api|ai|frontend|docs`；
- 提交规范：`feat(data): ...` / `fix(api): ...` / `docs: ...`，每完成一个功能提交一次，禁止向 `main` 强推；
- 公共文件（`config/`、`schema`、统一响应）改动需经架构师确认。

### 7.4 系统测试计划

见《8.测试计划》（待产出）。初步约定：

- 单元测试：由各模块负责人在编码阶段同步完成；
- 接口测试：验证 5 个聚合 API + `/api/chat` 的请求/响应符合契约；
- 集成测试：后期联调时执行，覆盖前后端全链路；
- 验收测试：检查清单见《团队分工协作规范》§七，达标后进入答辩。

### 7.5 需求管理计划

- 需求基线以《2.软件需求规约》为准，需求变更必须走 CCB 流程；
- 建立需求双向跟踪矩阵（需求 → 设计 → 代码 → 测试用例），每里程碑核查覆盖情况；
- 与《项目解析.md》口径保持一致，禁止出现与既有文档矛盾的表述。
