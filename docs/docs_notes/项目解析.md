# 智慧医疗大数据与 AI 大模型分析平台 — 项目解析

> 本文档基于《智慧医疗大数据与AI大模型分析平台.docx》整理，用于项目立项、需求理解与方案决策参考。

---

## 一、项目一句话定性

做一个**医疗大数据分析平台**：把真实的医院住院患者出院数据集（Hospital Inpatient Discharge Data，约 33 个字段）经过「清洗 → 入库 → 多维分析 → API 化 → 自然语言交互 → 图表可视化」的完整大数据链路，最终让用户**用自然语言提问，就能得到文字洞察 + 动态图表**。

- **难度系数**：★★★★★
- **项目性质**：大数据实训/大作业类项目（要求 CMMI3 / RUP / 敏捷过程规范、Git 按功能提交、标注"适配项目实训场景"）。
- **重点提示**：**大数据处理与分析是主线，AI 只是"辅助交互入口"**（文档反复强调）。答辩/报告时不要把重点放反。

## 二、核心目标与价值定位

文档明确了四个价值落点，是后续写报告、答辩要反复扣的关键词：

| 价值方向 | 对应实现 |
|---|---|
| 医疗资源优化 | 按医院 / 区域 / 疾病的住院时长、住院量分布分析 |
| 疾病趋势预测 | 按年份 / 疾病（CCSR）的发病率与费用趋势 |
| 医疗成本控制 | Total Charges / Total Costs 分布、支付方式占比 |
| 数据支撑决策 | 多维聚合 + 洞察报告 |

## 三、系统三大核心模块（含一期 / 二期边界）

系统由三个模块组成，每个模块明确拆分了「一期（基础必做）」和「二期（进阶加分）」。

### 模块一：数据预处理与持久化模块（大数据核心）

> 职责：数十万条原始数据的读取、清洗、标准化、去重，入库 MySQL，增量更新与备份。

| 功能 | 说明 | 阶段 |
|---|---|---|
| 大数据批量读取 | 高效读 TSV/CSV，兼容数十万条，解决卡顿/内存溢出 | 一期 |
| 大数据异常处理 | 缺失值/异常值/去重；例：非新生儿 `Birth Weight` 置 N/A、去重复住院记录 | 一期 |
| 数据类型标准化 | 例：`Total Charges` 去逗号转 float、日期/编码标准化 | 一期 |
| 结构化入库 | 存 MySQL，合理表结构 + 索引优化 | 一期 |
| 数据质量评估 | 完整性/准确性/一致性/时效性四维评分 + 可视化报告 | 二期 |
| 数据备份与恢复 | 定时任务 + HDFS | 二期 |
| 大数据增量更新 | 识别差异、避免重复入库 | 二期 |

### 模块二：大数据分析服务模块（大数据核心）

> 职责：多维聚合、算法封装，通过 RESTful API 对外服务。

| 功能 | 说明 | 阶段 |
|---|---|---|
| 多维度聚合分析 | 按疾病/年龄段/医院/年份聚合，算平均住院时长、总费用分布、支付方式占比 | 一期 |
| 大数据算法封装 | 均值、占比、分布统计、异常值识别等 | 一期 |
| API 响应标准化 | 统一 JSON（结果 + 维度信息 + 指标说明 + 查询耗时） | 一期 |
| 复杂医疗大数据分析 | 疾病关联、费用预测、再入院风险（机器学习） | 二期 |
| API 性能优化 | 缓存 + Redis + 查询优化 | 二期 |
| 异常处理机制 | 参数校验、超时/大数据量保护 | 二期 |

### 模块三：AI 智能交互模块（辅助交互）

> 职责：用户自然语言入口，解析意图 → 调用服务层 API → 生成文字摘要 + ECharts 图表。

| 功能 | 说明 | 阶段 |
|---|---|---|
| 智能工具调用 | LangChain 解析意图 → 匹配对应 API | 一期 |
| 分析结果文本生成 | LLM 把 JSON 转通俗文字摘要 | 一期 |
| 大屏可视化 | 自动生成 ECharts 图表配置 | 一期 |
| 医疗洞察报告生成 | 基于多轮/深度分析生成报告 | 一期 |
| Web 交互界面 | 聊天式界面（HTML/CSS/JS + Vue） | 一期 |
| 意图识别优化 | 模糊/多维/术语联想，准确率 ≥90% | 二期 |
| 多轮对话记忆 | 上下文关联查询 | 二期 |
| 可视化进阶 | 3D/地图/动态时序 + 交互（筛选、放大、下载） | 二期 |
| LLM 本地化部署 | BaiChuan/Qwen + FastAPI，保障数据隐私 | 二期 |

## 六、数据集详解（33 个字段，按业务分组）

数据源为纽约州 SPARCS 类似的住院出院数据，样例行集中在 Bronx（布朗克斯）的 Montefiore 医院。字段按业务分组：

| 分组 | 字段 | 说明 |
|---|---|---|
| **医院/机构** | Hospital Service Area、Hospital County、Operating Certificate Number、Permanent Facility Id、Facility Name | 服务区域、县、证书编号、永久ID、医院名 |
| **人口统计学** | Age Group、Zip Code-3、Gender、Race、Ethnicity | 年龄组、邮编前3位、性别、种族、民族 |
| **就诊信息** | Length of Stay、Type of Admission、Patient Disposition、Discharge Year | 住院天数、入院类型、离院去向、出院年份 |
| **诊断(CCSR)** | CCSR Diagnosis Code/Description、CCSR Procedure Code/Description | 诊断/操作代码及描述（临床分类软件精炼版） |
| **DRG/严重程度** | APR DRG Code/Description、APR MDC Code/Description、APR Severity of Illness Code/Description、APR Risk of Mortality、APR Medical Surgical Description | 诊断相关组、主要诊断类别、病情严重程度、死亡风险、内/外科 |
| **支付方式** | Payment Typology 1/2/3 | 主/次/第三支付方 |
| **临床指标** | Birth Weight、Emergency Department Indicator | 出生体重(克)、是否经急诊 |
| **费用** | Total Charges、Total Costs | 总费用、总成本 |

**样板数据观察到的分析点（可直接作为功能用例）：**

- 常见疾病：COVID-19、尿路感染、剖宫产、多发性硬化、脑外伤等
- `Length of Stay` 是核心分析指标（平均住院时长）
- `Total Charges` 带逗号分隔（如 `320,922.43`），对应"去逗号转 float"清洗需求
- `Birth Weight` 在非新生儿行为空，对应"非新生儿置 N/A"规则
- 支付方式有 Medicare/Medicaid/Private Health Insurance 等，适合做占比分析

## 七、文档疑点与注意事项（坑）

文档有明显**模板套用痕迹**，做项目和写报告时需注意：

1. **爬虫需求是模板残留**：技术表里写"Scrapy 采集互联网上的**就业信息**"——这是从"就业大数据分析"模板复制来的，与医疗项目无关。医疗数据集是**本地提供，不需要爬虫**。建议报告中处理掉或弱化"就业信息"字样。

2. **数据量前后矛盾**：
   - 正文写"数据量共计 **200万+**"
   - 模块职责里多处写"**数十万条**"
   - 结论：需统一口径（本地实训用几十万条，理论上支撑 200万+）。

3. **图/表编号混乱**：出现"图7-1/7-2/7-3/7-4"、"表7-1"——说明是从某文档第 7 章截取。落报告时要理顺编号。

4. **章节编号风格不统一**：正文用"（1）（2）"，开发要求用"1）2）"，照抄显粗糙。

5. **"大数据 vs 实际体量"的落差**：文档要求 Hadoop/Spark/Hive 全套，但实训单机环境通常 Pandas + MySQL 就够。需提前决策：真搭集群，还是"单机模拟 + 预留 Spark/Hive 接口"。

## 八、推荐实施路线

按「数据 → 分析 → AI → 前端」依赖顺序推进：

1. **阶段 0：环境与数据准备** — 确认数据集字段是否与 33 字段一致，搭环境
2. **阶段 1：数据处理与持久化（模块一·一期）** — 分块读取 → 清洗规则 → 建表索引 → 批量入库
3. **阶段 2：分析服务（模块二·一期）** — 聚合维度 → Flask API → 统一 JSON
4. **阶段 3：AI 交互（模块三·一期）** — LangChain Agent → 意图→API 映射 → LLM 摘要 → ECharts 配置
5. **阶段 4：前端展示（模块三·一期）** — Vue 聊天界面 → 接 AI 层 → ECharts 渲染
6. **阶段 5：二期加分项（按剩余时间选做）** — 优先：API 缓存、异常处理、多轮对话、意图优化；次选：质量报告、可视化进阶、LLM 本地化、备份/增量

## 九、关键技术决策点

| 决策 | 影响 | 建议默认值 |
|---|---|---|
| Hadoop/Spark/Hive 真集群还是模拟？ | 决定复杂度天花板 | 单机 Pandas 为主，预留 Spark 接口 |
| LLM 云端 API 还是本地模型？ | 一期用云端，二期要求本地 | 一期云端，二期 Qwen/BaiChuan + FastAPI |
| 数据量定多少？ | 几十万（本地可跑）vs 200万+（需 Spark） | 几十万，统一口径 |
| 爬虫是否保留？ | 数据集本地提供 | 砍掉或弱化 |
