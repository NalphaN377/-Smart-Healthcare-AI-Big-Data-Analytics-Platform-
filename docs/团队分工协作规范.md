# 智慧医疗大数据项目 — 团队分工与协作规范

> 适用团队规模：5 人。核心原则：**架构先行定契约 → 数据层打通 → 其余并行 → 最后联调**。
> 目的：避免"一人干、四人等"，让每个人都能独立推进。

---

## 一、角色分工（5 人）

| 角色 | 主责模块 | 对应代码 | 一期交付物 | 二期方向 |
|---|---|---|---|---|
| **① 项目负责人 + 架构师** | 总体架构、接口契约、过程文档 | `sql/` `config/` 接口规范 | DB schema、API 契约、Git 规范、进度管控 | 集成测试、CMMI3/RUP 报告 |
| **② 数据工程师** | 模块一：预处理与持久化 | `app/data_layer/` | 清洗入库流水线跑通、数据质量报告 | 质量评估、增量更新、备份恢复 |
| **③ 后端工程师** | 模块二：分析服务 | `app/service_layer/` | 5 个聚合 API + 统一 JSON | Redis 缓存、参数校验、异常处理、复杂分析 |
| **④ AI 工程师** | 模块三：AI 交互（后端） | `app/ai_layer/` | 意图识别 + LLM 摘要 + 图表配置 | LLM 语义意图、多轮对话、本地化部署 |
| **⑤ 前端工程师** | 展示层 | `frontend/` | 聊天界面 + ECharts 渲染 | 图表交互、3D/地图、历史记录 |

**选人建议**：
- ②③④ 需要 Python 扎实；④ 额外要懂 LLM/LangChain；⑤ 要 Vue + ECharts。
- ① 不一定要写最多代码，但必须**沟通强、能定标准**——这个人是团队是并行还是互相等的关键。

## 二、接口契约（契约先行，解耦关键）

模块依赖链：

```
数据层(②) ──> 服务层(③) ──> AI层(④) ──> 前端(⑤)
                └── 前端也直接依赖服务层
```

若⑤等④等③等②，就是串行开工，前两周只有一人干活。**解法是①在第一周冻结三份契约，其余人对着契约写 mock，不必等上游真完成：**

1. **DB 契约**：`sql/schema.sql` 的 33 字段 + 索引
2. **API 契约**：请求/响应 JSON 格式（`app/common/response.py` + `app/service_layer/api/routes.py` 已定义 5 个接口 + `/api/chat`）
3. **数据列名映射**：`app/data_layer/storage.py` 中的 `COLUMN_MAPPING`

> 这三份契约在项目骨架中已经写好。① 的第一件事是**通读骨架、把契约拍板成"定稿"，再发给大家**。

**统一响应格式（API 契约核心）**：

```json
{
  "code": 0,
  "message": "success",
  "data": { "rows": [...] },
  "meta": { "dimension": "age_group", "elapsed_ms": 123 }
}
```

**现有 API 清单**：

| 接口 | 方法 | 用途 |
|---|---|---|
| `/api/health` | GET | 健康检查 |
| `/api/aggregate` | GET | 通用多维度聚合 |
| `/api/avg_length_of_stay` | GET | 平均住院时长 |
| `/api/cost_distribution` | GET | 总费用分布 |
| `/api/payment_ratio` | GET | 支付方式占比 |
| `/api/year_trend` | GET | 出院年份趋势 |
| `/api/chat` | POST | AI 自然语言问答 |

## 三、Git 协作规范

文档硬性要求：*"使用 Git 版本控制，提交记录规范，每完成一个功能提交一次，标注提交说明"*。

### 分支策略

```
main                 # 只放稳定可运行版本
├── feature/data      # ② 数据层
├── feature/api       # ③ 服务层
├── feature/ai        # ④ AI 层
├── feature/frontend  # ⑤ 前端
└── feature/docs      # ① 文档/契约
```

### 提交规范（提交说明格式）

```
feat(data): 完成 Total Charges 去逗号转 float
fix(api): 修复 aggregate 维度白名单校验
docs: 更新团队分工规范
```

**规则**：
- 每人每天至少一次提交；合并到 `main` 前必须能跑通自己的部分。
- 冲突由 ① 统筹解决；禁止直接向 `main` 强推（force push）。

## 四、里程碑与时间线（以 4-6 周为例）

| 阶段 | 周期 | 谁主攻 | 产出 | 其他人 |
|---|---|---|---|---|
| **0 环境+契约** | 第 1 周 | ① | git init、装依赖、冻结 3 份契约、DB 建表 | 全员装环境、读骨架、写自己模块 mock |
| **1 数据打通** | 第 2 周 | ② | 清洗入库流水线跑通、出样例数据 | ③④⑤ 用 mock 数据并行开发 |
| **2 服务+前端** | 第 3 周 | ③⑤ | API 全部可用、前端界面成型 | ④ 接 ③ 的 mock API 开发 AI 层 |
| **3 AI+联调** | 第 4 周 | ④ | `/api/chat` 闭环、前后端联调 | ② 补二期、① 做集成测试 |
| **4 二期+报告** | 第 5-6 周 | 全员 | 按需加二期加分项、写过程文档 | 各自写模块文档 |

**贯穿全程**：每周一次 15 分钟站会（进度 / 阻塞 / 下一步），① 负责更新任务看板。

## 五、过程文档分工（CMMI3 / RUP 硬要求）

过程规范要求 CMMI3、RUP、敏捷，这些是评分点，建议**边做边写**，不要最后补：

- 全员轮流：会议纪要、周报、迭代回顾

## 六、协作约定与常见坑

| 坑 | 规避方法 |
|---|---|
| **② 是瓶颈**（所有人等数据） | ② 先产出**小样例数据集**（1 万条即可）给 ③④⑤ 联调，不必等几十万条全入库 |
| **④ 没 LLM key 就卡住** | AI 层已有模板摘要 fallback（无 key 也能跑），先用规则+模板开发，key 到位再接真 LLM |
| **联调才发现字段对不上** | 强制所有人只用 `COLUMN_MAPPING` 和 API 契约，不许自造字段名 |
| **前端写死假数据** | 用 `client.js` 统一封装，联调时只改 base URL，不散落各处 |
| **测试没人写** | 规则：谁写的代码谁写单测，① 只负责集成测试和验收 |
| **合并冲突频繁** | 各分支只改自己目录，公共文件（config/schema/response）改动需经 ① 确认 |
